# Knife Knowledge Base

An open, practical knowledge base on kitchen knives—covering steels, blade geometry, construction, sharpening, maintenance, safety, and product education.

## Purpose

This project is designed for practical learning, commercial training, customer education, and marketing content. It is not intended to be an academic paper or a substitute for manufacturer-specific technical documentation.

The goal is to make knife knowledge easier to understand without turning useful simplifications into misleading claims.

## Website

The knowledge base is published as a searchable multilingual website with GitHub Pages:

**https://francescocmazza.github.io/knife-knowledge-base/**

The current active languages are:

- English (`en`) — the source of truth;
- Italian (`it`);
- Simplified Chinese (`zh-Hans`).

Other locale definitions remain in the repository for possible future use, but they are currently inactive and are not built, validated, exported, or published.

The site includes a language selector. English is published under `/en/`, Italian under `/it/`, and Simplified Chinese under `/zh-Hans/`.

## Source-of-truth language

English is the sole source-of-truth language for this project.

All technical or factual changes must first be made in the English files under:

```text
content/en/
```

The committed translations live under:

```text
translations/it/
translations/zh-Hans/
```

Translations are **not generated by GitHub Actions** and the publishing pipeline makes **no paid translation API calls**. Italian and Simplified Chinese translations are updated during editing and committed to the repository before publication.

Each translated Markdown file contains a `source_hash`. The build system compares that hash with the current English source. If the English source changes, the corresponding translation becomes **stale** until it is refreshed.

Production publication refuses to publish missing or stale active translations. This prevents an Italian or Chinese page from silently displaying English content.

# Editing the knowledge base — step by step

This section describes the normal editing workflow. For routine content changes, follow it in this order:

```text
Edit English → create branch/PR → refresh IT + zh-Hans → validate → merge → regenerate PDFs
```

## 1. Find the content you want to edit

The master content is the English Markdown under:

```text
content/en/
```

The main sections currently include:

```text
content/en/index.md                         Home page
content/en/01-foundations/                 Foundations
content/en/02-steels-and-metallurgy/       Steels and metallurgy
content/en/03-blade-construction/           Blade construction
content/en/04-geometry-and-bevels/          Geometry and bevels
content/en/05-knife-types/                  Knife types
content/en/08-use-and-safety/               Use and safety
content/en/10-sharpening/                   Sharpening
content/en/assets/                          Images and other content assets
```

Each article is a `.md` Markdown file.

For example, the article about burr formation is stored under the sharpening section, while Damascus-related material is stored under blade construction.

## 2. Edit an existing article directly on GitHub

For a simple text correction, no local software is required.

1. Open this repository on GitHub.
2. Click **Code**.
3. Open `content` → `en`.
4. Open the appropriate section folder.
5. Open the `.md` file you want to change.
6. Click the **pencil icon** in the upper-right corner: **Edit this file**.
7. Edit the text in the browser.
8. Use the **Preview** tab when useful to check the rendered Markdown.
9. Click **Commit changes…** when the edit is ready.

Markdown is ordinary text. Typical syntax is:

```markdown
# Main title

## Section title

Normal paragraph text.

- Bullet point
- Another bullet point

**Bold text**

[Link text](https://example.com/)
```

When editing an existing page, preserve existing Markdown structure, links, image paths, code, model numbers, steel grades, HRC values, measurements, and other technical data unless those elements are intentionally being changed.

## 3. Do not normally commit English content changes directly to `main`

When GitHub asks where the edit should be committed, the recommended choice for knowledge-base content is:

**Create a new branch for this commit and start a pull request.**

Use a short descriptive branch name, for example:

```text
update-sharpening-content
clarify-damascus-section
fix-safe-carrying-guidance
```

Why this matters:

- changing English immediately changes the expected `source_hash` for the matching translations;
- Italian and Simplified Chinese therefore become stale until refreshed;
- the pull request gives us a safe place to update the English source and both translations together;
- GitHub Actions can validate everything before the change reaches `main`.

A temporary red translation-validation check on a new PR is therefore not necessarily a problem: it can simply mean that the English edit has been made but the corresponding translations have not yet been refreshed.

## 4. English is always edited first

If a change affects meaning, facts, recommendations, technical explanations, specifications, or structure, change the English source first.

Do **not** make a factual change only in Italian or Chinese while leaving English different. English remains authoritative.

Examples of changes that must start in English:

- correcting a technical claim;
- adding or removing a paragraph;
- changing a steel specification;
- changing an HRC value;
- adding a safety warning;
- reorganizing a section;
- adding a new article;
- deleting or renaming an article.

A purely linguistic correction to an existing translation—such as improving Italian wording without changing meaning—may be made directly to the translated file, provided the English source is unchanged.

## 5. Refresh the Italian and Simplified Chinese translations

After an English article changes, update only the corresponding stale translations under:

```text
translations/it/
translations/zh-Hans/
```

The translated folder structure mirrors `content/en/`.

Example:

```text
content/en/10-sharpening/the-burr.md
translations/it/10-sharpening/the-burr.md
translations/zh-Hans/10-sharpening/the-burr.md
```

The normal approach is to ask Claude Code to:

1. inspect the current branch;
2. identify only the missing/stale active translations;
3. translate those pages from the current English source;
4. preserve Markdown, links, image paths, technical values, product names and terminology;
5. update the required `source_hash` metadata;
6. validate until the active scope reports `0 missing, 0 stale`;
7. commit and push the translation updates to the same branch/PR.

The active translation scope is only:

```text
en
it
zh-Hans
```

Do not spend time translating or validating inactive locales unless they are deliberately reactivated in the future.

## 6. Validate before merging

The strict validation command used by the project is:

```bash
python scripts/multilingual_site.py --require-translations
```

For the active scope, the desired result is:

```text
0 missing
0 stale
```

GitHub Actions also performs validation automatically on pull requests.

Before merging a content PR, confirm that the relevant checks are green, especially:

- **Deploy multilingual knowledge base to GitHub Pages**;
- **Export multilingual guide**;
- **Export PDF guides** when the PDF workflow is triggered by the changed paths.

Do not merge a content change while active translations are still missing or stale.

## 7. Merge the pull request

Once:

- the English content is correct;
- Italian is current;
- Simplified Chinese is current;
- validation reports no missing/stale active translations;
- GitHub Actions checks are green;

then the pull request can be merged into `main`.

`main` should represent a fully publishable snapshot of the knowledge base.

## 8. Adding a new article

When adding a new article:

1. create the new English `.md` file under the appropriate `content/en/` section;
2. follow the style of nearby articles;
3. add the page to `mkdocs.yml` if it must appear in the website navigation;
4. create the matching Italian translation under `translations/it/`;
5. create the matching Simplified Chinese translation under `translations/zh-Hans/`;
6. validate with `--require-translations`;
7. confirm GitHub Actions is green;
8. merge the PR.

A new English article without matching active translations will intentionally fail strict multilingual validation.

## 9. Renaming, moving, or deleting an article

Treat structural changes carefully because the English and translation trees must remain aligned.

For a rename or move:

1. rename/move the English file;
2. rename/move the corresponding Italian file;
3. rename/move the corresponding Simplified Chinese file;
4. update `mkdocs.yml` navigation and any internal links that point to the old path;
5. refresh translation metadata if required;
6. run strict validation before merging.

For a deletion, remove the corresponding translated pages and update navigation/internal links as necessary.

## 10. Editing or adding images

Content images used by the English source belong under the repository's approved asset structure, principally:

```text
content/en/assets/
```

When adding or replacing an image:

1. confirm that the project has the right to publish it;
2. use a stable descriptive filename;
3. add or replace the asset in the repository;
4. update the Markdown or visual configuration that references it;
5. check the website rendering;
6. check the PDF export if the image is intended to appear in the printed guide.

Do not upload confidential manuals, proprietary slide decks, or third-party images unless there is clear permission to publish them.

See [`content/en/assets/IMAGE_RIGHTS.md`](content/en/assets/IMAGE_RIGHTS.md) for the image-rights rules.

## 11. Editing only the README or repository documentation

Files such as:

```text
README.md
PUBLISHING_GUIDE.md
CONTRIBUTING.md
```

are repository documentation, not English knowledge-base source pages.

Editing those files does **not** by itself make Italian or Chinese article translations stale, because translation hashes are based on the English content under `content/en/` and the translation configuration/glossary inputs used by the builder.

## 12. Generate the latest PDFs after a merge

PDFs are generated through GitHub Actions rather than stored as permanent release files in the repository.

After the desired content has been merged into `main`:

1. open the repository on GitHub;
2. click **Actions**;
3. select **Export PDF guides**;
4. click **Run workflow**;
5. make sure the selected branch is **`main`**;
6. choose the language:
   - `all` for all active languages;
   - `en` for English only;
   - `it` for Italian only;
   - `zh-Hans` for Simplified Chinese only;
7. choose whether editorial placeholders should be hidden or shown;
8. normally choose **hide** for a clean reader-facing PDF;
9. click **Run workflow**;
10. wait for the workflow to finish with a green check.

The PDF workflow is restricted to active locales. It will not export an inactive language accidentally.

Translated PDF builds use strict translation validation, so a stale Italian or Chinese edition cannot silently be generated using English fallback text.

## 13. Download the generated PDFs

Once the PDF workflow is green:

1. open that workflow run;
2. click **Summary** in the left sidebar if you are currently viewing the `export-pdf` job details;
3. scroll down to the **Artifacts** section;
4. click the artifact named approximately:

```text
knife-knowledge-base-pdf-<run number>
```

GitHub downloads the artifact as a ZIP file.

Extract the ZIP to obtain the generated PDFs. When `all` was selected, the package contains the current PDFs for all active languages.

For an official/current export, prefer a successful workflow run generated from the latest `main` commit rather than an older artifact generated from a feature or pull-request branch.

## 14. Generate the multilingual website/export package

For a downloadable website/Markdown snapshot rather than PDFs:

1. open **Actions**;
2. select **Export multilingual guide**;
3. run the workflow on `main`;
4. wait for a green result;
5. download the generated artifact from the run's **Summary** page.

The export contains the built website and the corresponding per-locale source trees for the active languages.

## 15. Quick checklist for a normal content edit

Before considering an edit finished, verify:

- [ ] I edited the English source under `content/en/` first.
- [ ] I used a branch/PR rather than publishing an unfinished English change directly to `main`.
- [ ] I refreshed only the affected Italian translation(s).
- [ ] I refreshed only the affected Simplified Chinese translation(s).
- [ ] Active validation reports `0 missing, 0 stale`.
- [ ] GitHub Actions checks are green.
- [ ] The PR has been merged into `main`.
- [ ] If new PDFs are needed, I ran **Export PDF guides** on `main` after the merge.
- [ ] I downloaded the PDF artifact from the workflow **Summary** page.

## Publishing and multilingual export architecture

The publishing pipeline builds the website from committed repository files.

English remains authoritative. Italian and Simplified Chinese are committed translations. GitHub Actions validates that active translations correspond to the current English source before production publication.

There is no OpenAI API, GitHub Models API, or other paid translation API in the publishing pipeline.

See [PUBLISHING_GUIDE.md](PUBLISHING_GUIDE.md) for additional operating details.

## Current content scope

The current knowledge base covers:

- the five main dimensions used to explain knife steel;
- alloying elements;
- monosteel, clad, Damascus, and full Damascus construction;
- the self-sharpening effect in selected full Damascus blades;
- single- and double-bevel geometry;
- major knife types and cutting styles;
- safe use and carrying;
- water-stone preparation;
- burr formation, detection, and removal;
- a practical sharpening workflow.

See [the English content index](content/en/README.md).
